# Orders

## Overview

Everything after the customer presses Pay: the signed Stripe webhook that marks an order paid and records refunds, the daily reconcile cron that replays lost Stripe events and syncs pending refunds, and the admin order list and order page with their actions (ship, deliver, undo, tracking, notes, the attention flag, refunds with restock, cancel). The checkout side (the email and address form, `startCheckout`, `/checkout/complete`) lives in `src/features/checkout/`. Order writes that both features need live in `src/lib/orders/`. Governing specs: [0006 Card payment and paid orders](../../../docs/specs/0006-card-payment-paid-orders/index.md), [0007 Shipping address and flat rate](../../../docs/specs/0007-shipping-address-flat-rate/index.md) (address, phone and delivery on the admin pages), [0008 Purge PII from expired orders](../../../docs/specs/0008-purge-expired-order-pii/index.md), [0010 Admin order management](../../../docs/specs/0010-admin-order-management/index.md) (statuses, refunds, restock, search and filters).

## Files

- `webhook.ts`: `POST /api/stripe/webhook`. Verifies the `Stripe-Signature` with `STRIPE_WEBHOOK_SECRET` (400 otherwise), then calls `handleStripeEvent`.
- `stripe-events.ts`: `handleStripeEvent`, the one path from a Stripe event to an order change, shared by the webhook and the cron. Also `expireCatalogTags`.
- `event-decision.ts`: pure. The four handled `checkout.session.*` types and what each one decides, the three `refund.*` types, and `refundOutcome`, what a Stripe refund status means (unknown values are never guessed).
- `reconcile.ts`: `GET /api/cron/reconcile-orders` (daily in `vercel.json`). Replays the decisive Stripe event for pending orders older than 90 minutes, then syncs pending refunds (`refund-sync.ts`), both inside one 50 second budget (`RECONCILE_BUDGET_MS`). Each order's or refund's failure is caught, logged and counted as skipped, and flagged (`needs_attention`) orders are read last, so no single order can stall the batch.
- `actions/`: the admin server actions, `status.ts` (`markShipped`, `markDelivered`, `undoStatus`, `editTracking`), `notes.ts` (`addNote`, `resolveAttention`), `refund.ts` (`refundOrder`, `checkRefundWithStripe`), `cancel.ts` (`cancelOrder`, paid and pending). Shared, server only: `guard.ts` (lock the order, then the stale, in flight and status checks) and `refund-steps.ts` (send the reserved refund to Stripe, settle its answer, expire caches).
- `order-lock.ts`: `lockOrderByNumber` / `lockOrderById` (`FOR UPDATE`), `hasRefundInFlight`, `isStale`, `loadRefundLedger`.
- `order-actions.ts`: pure. `statusAllows` / `allowedActions`, which actions an order allows, and the in flight and "Check with Stripe" timings.
- `refund-math.ts`: pure. The `RefundLedger` math: remaining, refundable units, the suggestion and caps, the cancel plan, the restock allocation.
- `refunds.ts`: the refund flow, `reserveRefund` (under the order lock), `requestStripeRefund` (no transaction open, the refund id as idempotency key), `applyRefundOutcome` (the one settle path for the action, the webhook and the sync), `restockRefund`, `recordSystemRefund` (a dashboard refund).
- `refund-sync.ts`: `syncRefund` (one refund, the order page button) and `syncPendingRefunds` (the cron's batch).
- `schemas.ts`, `messages.ts`, `list-params.ts`: pure. Action inputs, action errors with the fixed words the admin sees, and the list's search and filter params.
- `purge-expired.ts`: `GET /api/cron/purge-expired-orders` (daily in `vercel.json`, after reconcile). Blanks the personal data columns and the cart and customer links on orders expired more than `EXPIRED_ORDER_PII_RETENTION_DAYS` (30) ago, in `SKIP LOCKED` batches under a 50 second budget, and stamps `pii_purged_at`.
- `email-display.ts`: pure `emailDisplay`, what an admin page shows for an order's email (the email, "Personal data removed", or "Email missing").
- `admin-queries.ts`, `components/`: `/admin/orders` (search `q`, filters `status`, `attention`, `refund`, `from`, `to`, keyset paging with `?before=<number>`; the old `?view=all` means `status=all`) and `/admin/orders/[number]` (refunds, history, allowed actions, attention reasons).
- `src/lib/orders/transitions.ts`: the only code that changes `orders.status`: `markPaid`, `markExpired`, `flagLatePayment`, and the admin moves `markShipped`, `markDelivered`, `revertShipped`, `revertDelivered`, `markCancelled`, `revertCancelled`.
- `src/lib/orders/snapshot.ts`, `order-image.ts`, `minimum-charge.ts`: pure order line snapshot, line image pick, per currency Stripe minimum.
- `src/lib/orders/session-state.ts`: pure `sessionState`, what a Checkout Session's `status` and `payment_status` pair means (`open`, `paid`, `processing`, `expired`, `unknown`).
- `src/lib/stripe.ts`: the Stripe client (pinned `STRIPE_API_VERSION`) and `stripeDashboardUrl`. `src/lib/cron-auth.ts`: `isCronRequest`, the constant time Bearer check every cron uses.

## Conventions

- Only `handleStripeEvent` marks an order paid. The cron never decides paid itself; it fetches the real event from Stripe and replays it through the same handler. Expiry without an event (a checkout restart, an order with no session) still goes through `markExpired`.
- The `stripe_events` insert (`ON CONFLICT DO NOTHING`) and the order change share one transaction. A replay finds its row and does nothing, and a thrown error rolls both back so Stripe's retry does the work again (the route answers 500).
- Decide on a Checkout Session's `status` and `payment_status` only through `sessionState`, never by reading them directly (passing the raw value into a note or log is fine), so the webhook, the cron, a checkout restart and the confirmation page cannot disagree. `unknown` (a value newer than the pinned API version) means money may have moved: no caller pays, expires or replaces an order on it.
- Every write that changes an order's status is guarded by the status it moves from (`pending_payment` for the payment paths; `flagLatePayment` by `cancelled` or `expired`). Zero rows updated means another path already moved it, so do nothing else. That includes side writes like the reconcile flag.
- Admin actions lock the order row first (`guard`), then check, in this order: the form's `updated_at` (stale), a refund in flight, the status. Every writer of an order row sets `updated_at = now()` itself (raw SQL skips `@updatedAt`); `addNote` is the one write that does not.
- Never hold a database transaction across a Stripe call. A refund is reserved pending under the order lock, sent to Stripe, then settled through `applyRefundOutcome`, which locks the order then the refund and moves the row only out of the status it read, so the action, webhook and sync can race. A pending refund counts against what is left to refund.
- A Stripe error the refund request could not have survived (invalid request, permission, authentication, card) marks it failed; anything else, idempotency errors included, leaves it pending for the sync.
- The order is found from the session's `metadata.order_id`, never from anything the browser sent. Foreign, unhandled and stale events answer 200 and change nothing.
- Stock is taken on paid with a locked `LEAST` update, so it never goes below 0. A shortfall or an amount or currency mismatch still marks the order paid, sets `needs_attention` and writes an event explaining why.
- After a paid commit or a restock, expire `catalog` and each affected `product:<slug>` tag: `revalidateTag(tag, { expire: 0 })` in the webhook and cron, `updateTag` in the server actions.
- Read an order's address only through `withDeliveryAddress` with `deliveryAddressColumns` (`src/lib/shipping/address.ts`); an order made before spec 0007 has none and shows "No address recorded". The phone is shown on admin pages only, inside the address block.
- `orders.email` is nullable only because of the purge. Decide what to show on `piiPurgedAt` (through `emailDisplay`), never on a null email: a null email on an order not purged is a bug, logged as `order.email_missing` where a page must keep working and thrown where the page is about one order. CHECKs in the migration SQL (invisible to Prisma drift detection) keep the email until the purge and allow the purge only on `expired` orders.
- The 30 day retention is the privacy policy's number (feature 16). Change `EXPIRED_ORDER_PII_RETENTION_DAYS` and the policy together; no env or setting overrides it.
- Both admin pages and every action call `requireAdmin()`. Dates show in `STORE_TIMEZONE`.
- Logs carry order ids, numbers and amounts, never an email or a card detail: `order.paid`, `order.expired`, `order.stock_shortfall`, `order.amount_mismatch`, `stripe.event.processed`, `stripe.event.failed`, `stripe.webhook.invalid_signature`, `cron.reconcile_orders`, `order.reconcile_unresolved`, `cron.reconcile_stripe_failed`, `cron.reconcile_order_failed`, `cache.tag_expiry_failed`, `cron.purge_expired_orders`, `cron.purge_expired_orders_failed`, `order.email_missing`, and for spec 0010 `order.shipped`, `order.delivered`, `order.status_reverted`, `order.tracking_updated`, `order.cancelled`, `order.attention_cleared`, `order.note_added`, `order.action_stale`, `refund.created`, `refund.succeeded`, `refund.failed`, `refund.stripe_refused`, `refund.stripe_unavailable`, `refund.restocked`, `refund.restock_skipped`, `refund.system_recorded`, `refund.late_failure`, `refund.unknown_status`, `cron.reconcile_refunds`, `cron.reconcile_refund_failed`. Reasons, notes and tracking numbers are never logged and never sent to Stripe. A failed query logs its SQLSTATE through `pgErrorCode` (`src/lib/db-errors.ts`), never the Postgres message, which can quote the row.

## Tests

Pure logic has `*.test.ts` beside it. The webhook, reconcile, admin queries and admin actions run against a real database in `tests/db/` (`pnpm test:db`), with events signed the way Stripe signs them (`tests/db/stripe-support.ts`) and the Stripe client stubbed at the edge. Flows are in `tests/e2e/checkout/` and `tests/e2e/admin/orders.spec.ts` (refund and cancel against real test mode payments under `STRIPE_E2E=1`, tagged `@stripe`). The hosted page test needs `STRIPE_E2E=1` and `stripe listen` running.
