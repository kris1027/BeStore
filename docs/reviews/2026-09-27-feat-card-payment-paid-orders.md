# Review, feat/card-payment-paid-orders, 2026-09-27

**Reviewed by**: Sonnet 5 (author on Sonnet 5)
**Scope**: 78 files, feat/card-payment-paid-orders vs main (merge base `329c4ec`)
**Verdict**: Changes requested

## Summary

This change implements spec 0006 end to end: the checkout email form and `startCheckout`, the signed Stripe webhook as the single idempotent path to `paid` (with stock decrement, shortfall handling, amount/currency mismatch flagging, and cache-tag expiry), the daily reconcile cron as a replay-based safety net, the customer confirmation page, and the admin orders list/detail. The implementation is careful and closely tracks the spec's invariants: prices and totals always come from the database under a cart row lock, the Stripe session is built only from the frozen order, `markPaid`/`markExpired` are the only status-changing functions and both use a `WHERE status = 'pending_payment'` guard, stock is taken with a lock-and-`LEAST` CTE that never goes negative, the `stripe_events` insert and the state change share one transaction so a thrown error rolls both back for Stripe's retry, and both admin pages call `requireAdmin()` themselves. Logging is disciplined about never including an email. Test coverage is excellent: pure logic is unit tested, the webhook/reconcile/checkout paths are exercised against a real Postgres including duplicate events, races for the last unit, concurrent checkout submits, and Stripe-unreachable paths, and Playwright covers the full webhook-to-admin flow plus a11y and keyboard use.

The one real defect is in the reconcile cron's "unresolved" fallback: it can flag a perfectly good, already-paid (or already-expired) order with a false `needs_attention` note claiming no Stripe event was found, because — unlike every other order-mutating write in this codebase — that write has no `status = 'pending_payment'` guard. This is reachable through the cron's own normal replay path, not just a contrived edge case, so it should be fixed before merge.

## Major

### 🟠 Reconcile can flag an order the webhook just resolved concurrently, `src/features/orders/reconcile.ts:88-94` and `:115-132`
**Problem**: `reconcileOrder` finds the order's decisive Stripe event and replays it: `const result = await handleStripeEvent(event); if (result === "paid" || result === "expired") return result;` (lines 89-91). `handleStripeEvent` also returns `"duplicate"` (the event's id already exists in `stripe_events`) and `"stale"` (the order already left `pending_payment`) for exactly the case where another path — most plausibly the real webhook delivery, which Stripe retries for up to three days and which can easily still be in flight when the daily cron runs — processed the same event or moved the same order first. Neither `"duplicate"` nor `"stale"` is handled by the `if`, so execution falls through to `flagUnresolved(order, session.status)` (line 93) even though the order was just correctly resolved. `flagUnresolved` then writes `db.order.update({ where: { id: order.id }, data: { needsAttention: true } })` (line 122) with **no `status: 'pending_payment'` guard** — unlike `markPaid`, `markExpired`, and `saveSessionId`, which all guard their writes this way for precisely this reason — so it unconditionally sets `needsAttention = true` and appends a `note` event reading "Stripe reports the checkout session as complete, but no Stripe event for it was found. Check the payment in the Stripe dashboard." on an order that is now `paid` (or `expired`) and entirely fine.
**Why it matters**: The reconcile cron exists specifically to cover the case where webhook delivery is delayed, which is exactly when this race is live — a webhook landing at nearly the same moment as the daily cron run is the cron's core scenario, not a rare corner case. The result is a false, misleading audit-trail entry and a `needs_attention` badge on a healthy paid order, which sends an admin to investigate a non-problem; since `needs_attention` isn't cleared anywhere until feature 10, this false positive is permanent until a human notices it's bogus. It also silently defeats the "note is written once" comment's intent, since the note now records something untrue rather than something rare-but-real.
**Suggested fix**: Make the "unresolved" write guarded the same way every other order mutation in this feature is: turn `flagUnresolved`'s update into `db.order.updateMany({ where: { id: order.id, status: "pending_payment" }, data: { needsAttention: true } })` and only create the `note` event when that update actually touched a row (mirroring `saveSessionId`'s `count === 1` check). That closes both this fall-through case and the narrower "no event found at all, but resolved a moment later" race, since a no-op update means someone else already decided the order's fate.

## Strengths

- The state-machine invariants are enforced at the SQL level, not just in application logic: every status-changing write in `src/lib/orders/transitions.ts` is `UPDATE ... WHERE status = 'pending_payment'`, and `stock_quantity` is taken with a `SELECT ... FOR UPDATE` CTE plus `LEAST` so it can never go negative and a shortfall is always visible. The `tests/db/stripe-webhook.db.test.ts` "sells the last unit once when two paid orders race for it" test proves the stable variant-id lock ordering actually prevents a double-sell under real concurrency, not just on paper.
- Idempotency is handled at exactly one place — the `stripe_events` insert and the order mutation share a single transaction in `handleStripeEvent`, so a thrown error (tested via a mocked `markPaid` that writes then throws) rolls back everything including the `stripe_events` row, letting Stripe's retry redo the work; the same-event-twice and completed-then-async-succeeded sequences are both covered.
- `startCheckout`'s restart path (`clearPendingOrder` in `src/features/checkout/actions/start-checkout.ts`) never sets a local `expired` while Stripe could still take the money: it branches only on Stripe's own session status, re-checks once if an expire call races a just-completed session, and reloads the order from the database (rather than trusting the Stripe response) to distinguish `already_paid` from `payment_processing`.
- Logging is consistently disciplined: every log call site in `src/features/orders/log.ts`, `src/lib/orders/log.ts`, and `src/features/checkout/log.ts` passes only ids, numbers, and amounts, and there's an explicit db test asserting the customer's email never appears in captured log output.

## Test coverage

Strong and layered. Pure logic (`event-decision`, `snapshot`, `minimum-charge`, `order-image`, `mask-email`, `stripe-session`) is unit tested including boundary cases. The webhook, reconcile, and checkout paths run against a real Postgres in `tests/db/*.db.test.ts` with events signed the way Stripe signs them, covering signature failures, duplicate/foreign/unhandled/stale events, rollback-on-throw, shortfalls, amount/currency mismatches, the two-orders-race-for-one-unit case, checkout restarts, and concurrent checkout submits. Playwright covers the full webhook-to-admin-detail flow, the admin 404 for non-admins, keyboard-only submission, and axe on every new page. The one gap is the race documented above: `reconcile-orders.db.test.ts`'s "flags an order whose session is over but whose event cannot be found, once" test only exercises the case where no event exists at all, never the case where `handleStripeEvent` returns `"stale"` or `"duplicate"` because another path just resolved the order — that path is untested as well as buggy.
