## Summary

This change builds the whole first buy loop end to end: the admin product create form (options, variants, price/stock, a signed-URL image upload), the storefront catalog under Cache Components (`'use cache'` reads tagged and expired on write), the signed HMAC cart cookie with a `SELECT ... FOR UPDATE` locked cart, the cart and checkout-summary pages, the expired-cart cron, and the admin-gate/sign-out rework needed to keep real HTTP statuses and a clean sign-out under Cache Components. I traced every acceptance criterion (AC-1 through AC-20) against the code and found the implementation matches the spec closely, including subtle ones that are easy to get wrong under Next 16 (stock counts never reaching the browser above the low-stock threshold, `refresh()` only from a Server Action, `instant = false` used consistently with the rest of the admin section, `CartLink` wrapped in its own `<Suspense>`). Money is integer cents throughout with a string-arithmetic `parseMoney`; prices are never accepted from the client; every admin surface calls `requireAdmin()`; cart line ownership is enforced by re-deriving the cart id from the verified cookie inside the same locked transaction. Test coverage is extensive: pure logic is unit tested, actions/queries/the cron run against a real Postgres in `tests/db/`, and the buy loop, cart, image upload, variants and accessibility are covered end to end in Playwright.

The one real gap is a narrow, pre-existing-pattern concurrency edge case in first-time cart creation, well below blocker/major severity. Nothing here should hold up the merge.

## Minor

### 🟡 Two concurrent first adds with no cart cookie yet can create two separate carts, `src/features/cart/actions.ts:63-72`
**Problem**: `addToCart` reads `cookieCartId` once, outside the transaction (line 45), then only takes the `SELECT ... FOR UPDATE` lock when a cookie id is already present (`lockLiveCart`, line 63). When two requests arrive with no cart cookie set yet — two browser tabs opened before either response returns, or a doubled first click — both see `cookieCartId === null` and both run `tx.cart.create` (line 72) in their own transaction. There is nothing to lock against because neither cart exists yet, so the two transactions don't serialize on anything and both commit, leaving two carts instead of one. Whichever response's `Set-Cookie` lands last in the browser "wins"; the item added in the other transaction is still in Postgres but no longer reachable from the visitor's cookie.
**Why it matters**: This is exactly the concurrency class called out for scrutiny in this review (cart caps under concurrency), and the existing test (`tests/db/cart-actions.db.test.ts`, "ends two concurrent adds for the last units at the cap") only exercises the locked path for a cart that already exists — it doesn't cover the no-cookie-yet race, so the gap is untested as well as unhandled. Impact is low (no double charge, no lost stock, the orphaned cart just expires and is swept by the cron) and the trigger is narrow (a genuine double-first-click or two tabs racing before any cookie exists), so this is not a blocker, but it is a real, reachable inconsistency in the one path this spec explicitly wanted correct under concurrency.
**Suggested fix**: Either give the visitor a client-generated cart id up front (e.g. mint the id before the first write and let `INSERT ... ON CONFLICT DO NOTHING` make creation idempotent), or serialize first-time creation with an advisory lock keyed off something stable enough to exist before the cart row does (e.g. a lock keyed by a short-lived idempotency value from the client). A cheaper mitigation is to disable the "Add to cart" control the instant the transition starts (it already does this for a second click on the same tab) and accept the two-tabs case as a documented, low-probability edge case if a real fix is judged not worth it for this slice.

## Nits

- ⚪ `src/lib/db-errors.ts:19-23`: `uniqueViolation` returns `""` (not `null`) when the SQLSTATE is `23505` but the constraint name regex fails to match. That's still treated as "a unique violation happened" by every caller, which is correct, but the empty string silently falls through `create-product.ts`'s `takenMessages` lookup to the generic `{ form: "unavailable" }` branch. Worth a one-line comment noting that's the intended fallback, so a future reader doesn't mistake it for a bug.
- ⚪ `src/features/admin-auth/log.ts:249`: the `.endsWith(".failed")` → `.endsWith("failed")` tweak (needed so the new `auth.proxy.lookup_failed` event logs as a warning) is easy to miss in the diff; a short comment on why the leading dot was dropped would save the next reader a re-derivation.

## Strengths

- The admin-gate rework (`proxy-decision.ts`'s `needsAdminGate`/`decideAdminGate` plus `proxy.ts`) is genuinely careful: it reuses the exact same `decideAdminAccess` verdict `requireAdmin()` uses, fails open only on a lookup error (logging `auth.proxy.lookup_failed`), and is unit- and integration-tested for every combination (disabled admin, no admin row, aal1 redirect preserving `next`, server actions and sign-out skipped, rsc/prefetch headers). It matches AC-19 precisely, including the "never grants" invariant.
- `sign-out.ts`'s route handler gets the small details right: Origin-header CSRF check before touching the session, 303 (not 302) so the browser re-fetches as GET, `Cache-Control: no-store`, and works from every session state including a session that can't be read at all — exactly what AC-20 asks for, with the client-side form-outside-the-menu-popup fix explained in a comment.
- The cart write path (`src/features/cart/actions.ts`, `src/lib/cart/`) locks the cart row with `FOR UPDATE` for every write, re-derives the cart id from the verified cookie rather than trusting a client-passed cart id, and the `tests/db/cart-actions.db.test.ts` suite proves the lock actually holds under `Promise.all` concurrent adds to an existing cart, not just in the logic on paper.
- `parseMoney` (`src/lib/money.ts`) does the cents conversion with string slicing and `Number.isSafeInteger`/`MAX_CENTS` bounds checking rather than any floating point arithmetic, and is unit tested at the currency-decimal and integer-overflow boundaries.
- The Next 16 Cache Components usage throughout (`'use cache'` + `cacheTag`/`cacheLife` in `queries.ts`, `updateTag` in the write path, `connection()` in the cron route to force request-time evaluation, `refresh()` used only inside `"use server"` actions, `<Suspense>` around every request-data read including the header cart count) matches the framework's documented model exactly, and `instant = false` on the two new admin pages is consistent with the rest of the admin section rather than a one-off shortcut.
- Accessibility coverage (`tests/e2e/catalog/a11y.spec.ts`) runs axe against every state named in AC-17 (empty cart, flagged cart, sold-out variant, checkout, a disabled option value), not just the happy path, and includes a keyboard-only add-to-cart flow.

## Test coverage

Strong and layered, matching the project's own convention: pure rules (`cart-lines`, `availability`, `picker`, `variant-grid`, `product-summary`, `money`, `slug`, `uuid`, `variant-label`, the cookie signature) are unit tested including edge cases (tampered signatures, malformed cookies, stock-vs-cap boundaries). Actions, queries and the cron run against a real Postgres in `tests/db/*.db.test.ts`, including the concurrent-add lock test and a same-cart-vs-other-cart ownership test for every cart line action. End-to-end Playwright covers the full admin-to-customer buy loop, cart edit/remove/reload persistence, stale-line flags with their one-click fixes, the image upload flow, the variant picker, and accessibility. The one gap is the narrow first-cart-creation race noted above under Minor, which is untested as well as unhandled; nothing else new or changed in this branch is untested.
