**Verdict**: Approve with nits

## Summary
This introduces `src/lib/orders/session-state.ts`, a single pure `sessionState()` function that maps a Checkout Session's `status`/`payment_status` pair to one of `open | paid | processing | expired | unknown`, and rewires all four prior call sites (`start-checkout.ts`, `checkout/queries.ts`, `orders/event-decision.ts`, `orders/reconcile.ts`) through it. I traced every branch against the pre-refactor logic for all reachable status/payment_status combinations (verified against the actual `stripe` v22 SDK types, which use `OtherString` widening, confirming `unknown` is a real, typed, reachable case, not a theoretical one) and confirm the standard paid/unpaid/no_payment_required × open/complete/expired matrix behaves identically before and after. Typecheck, lint, and the full Vitest unit suite (1025 tests) pass. The one real behavior change is that `unknown` sessions are now treated as "may already be settled" (keeps the order / shows "confirming") instead of the old implicit "not complete" fallback — a deliberate, well-reasoned, and safer choice per the module's own comment, but it is new branching logic with no test coverage anywhere in the diff or in the existing db-backed suites.

## Major
### 🟠 Untested `unknown` session-state branch in money-relevant code, `src/features/checkout/actions/start-checkout.ts:154` and `src/features/checkout/queries.ts:79`
**Problem**: `sessionState` can return `"unknown"` for any status/payment_status pair Stripe sends outside the three known values of each (the SDK types include `OtherString` specifically for this forward-compat case, so it is a real runtime possibility, not dead code). In `clearPendingOrder`, `state !== "expired"` routes `"unknown"` into `completedEarlier(...)` (keeps the old order, tells the customer to check confirmation). In `getCompletion`, the same state routes to `"confirming"`. Both are new decisions — the pre-refactor code's equivalent checks (`session.status === "complete"` / `session.status !== "complete"`) did not carve out this case the same way for a session whose `status` itself is unrecognized (as opposed to only its `payment_status`): the old `clearPendingOrder` would fall through to expiring and replacing the order for a non-"open"/non-"complete" status, and the old `getCompletion` would return `not_completed`. Neither the new `session-state.test.ts` nor any caller-level test (unit or `tests/db/*.db.test.ts`) exercises this branch through `clearPendingOrder` or `getCompletion`.
**Why it matters**: The task explicitly calls out this code as money-critical, and this is exactly the kind of branch (an unrecognized state on a live payment session) where a subtly wrong choice either strands a customer who already paid or lets them re-checkout and produce a duplicate paid session. The chosen behavior looks like the right call, but it is a genuine behavior change shipped with zero regression coverage, and the scope item's own "done when" bar is "every existing checkout, webhook and reconcile test still passes unchanged" — that bar doesn't require covering this new branch, but the branch is exactly the kind of thing this refactor was meant to make safer and testable in one place.
**Suggested fix**: Add a case to `session-state.test.ts` is not enough since the bug surface is in the callers, not in `sessionState` itself (which is already well tested). Add one `tests/db` case per caller (a mocked/stubbed session with a `status`/`payment_status` value outside the known enums) asserting `clearPendingOrder` keeps the order and `getCompletion` returns `"confirming"`, so this deliberate choice is locked in and future edits can't silently flip it back to the old, less-safe fallback.

## Nits

## Strengths
- The refactor achieves exactly what the scope item asked: one pure function, all four historical call sites now route through it, and I verified by hand (and by reading the actual `stripe` package's `.d.ts`) that every previously-reachable status/payment_status combination now produces the same output as before.
- `session-state.test.ts` covers the full 3×3 status/payment_status matrix plus the `unknown` cases (bad payment_status, null/unrecognized status), and the switch in `sessionState` is exhaustive (TS enforces it at every caller's exhaustive `switch`).
- No feature-boundary violations: the new module lives in `src/lib/orders/`, consistent with the existing `transitions.ts`/`snapshot.ts`/`minimum-charge.ts` pattern, and none of `checkout`/`orders` reach into each other's internals.
- Typecheck, lint, and the full unit suite (78 files / 1025 tests) pass clean; the standard-case db test fixtures (`tests/db/reconcile-orders.db.test.ts`, `tests/db/checkout-complete.db.test.ts`, `tests/db/start-checkout.db.test.ts`) all use status/payment_status combinations that this review confirmed are handled identically to before.

## Test coverage
`sessionState` itself is thoroughly unit tested. The gap is at the caller level: the new `unknown`-state behavior in `clearPendingOrder` (start-checkout.ts) and `getCompletion` (checkout/queries.ts) has no test anywhere in the repo, db-backed or otherwise — see the Major finding above.
